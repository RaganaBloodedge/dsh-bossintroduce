# 01 · 能力图谱（`capability-graph.json`）

> **这是整个系统的地基**：后面所有「生成」都必须且只能从这里取事实。
> 执行器只读它一个字段（`identity.name`，用于登录判定）；护栏读它全部 —— 它是**唯一事实源**。
>
> ⚠️ **图谱是个人数据，不属于 skill 引擎**。它放在**用户数据目录**（默认 `~/.auto-introduce/data/`），
> 不在 skill 目录里 —— 这样 skill 才能升级、分享、给别人用。位置由 `scripts/paths.mjs` 解析；
> 想知道当前读的是哪一份：`node scripts/flow.mjs where` 或 `python scripts/guard.py --where`。

`schema: capability-graph/v2`。文件名固定 `capability-graph.json`，默认取数据目录下的那一份，
可用 `guard.py --graph <path>` 或 `--data-dir <dir>` 覆盖。

---

## 一、字段结构

```
{
  schema, built_at, owner, tier_rule,
  sources:  { resume, resume_raw, links[], resume_docs[] },   # 事实从哪来（可追溯）
  identity: { name, gender_age, phone, email, homepage, graduation, note },
  education: [ { school, major, degree, period, jd_hits[] } ],
  honors:    { items[], jd_hits[], note },
  experience:[ { id, org, role, period, one_liner, highlights[], jd_hits[], blacklist[] } ],
  projects:  [ { id, on_resume, maturity, visibility, tier?, name, label_allowed[],
                 stack[], link, one_liner, highlights[], jd_hits[], blacklist[],
                 focus_aliases[]? } ],
  skills:    [ { group, items[], ceiling } ],
  global_blacklist: [ ... ],
  writing_rules: {
    number_policy, number_whitelist[], must_include[], structure[],
    budget: { resume_only:{min_chars,max_chars,target_chars[],max_sentences}, with_offresume:{...} },
    focus_aliases: { <id>: [别名...] }
  }
}
```

空架子直接从 `assets/capability-graph.template.json` 拷（`node scripts/init.mjs` 会自动落一份到数据目录）。

### 三个决定「能不能写」的字段

| 字段 | 含义 | 约束 |
|---|---|---|
| `on_resume` | **只表示"在不在简历上"，不是使用权限** | 两类事实都允许进自我介绍；`false` 的**必须额外给「链接 + 一句简略介绍」**（HR 在简历上看不到它，不给上下文等于没头没尾） |
| `visibility` | `public` / `private` | **`private` ⇒ 不可用**（没有公开链接，无法验证）。护栏在 `--focus` 时直接拒 |
| `jd_hits` | 这条事实能回应的 **JD 关键词** | **关键字段** —— 它把"我有什么"和"JD 要什么"接起来，是「点名」能力的实现基础 |

### 两处「按人可调」的配置（写死在引擎里就失去通用性）

| 字段 | 作用 |
|---|---|
| `writing_rules.number_whitelist` | **本人的技术栈**——放行哪些"看起来像数字但不是业绩"的写法（例：`C++20`、`Qt6`、`Gemma 2`）。每项 `{"label": 说明, "pattern": 正则}`；不给则用引擎内置的通用兜底 |
| `writing_rules.budget` | 文案长度纪律：`min_chars`/`max_chars` 是**硬失败闸门**，`target_chars` 是铁律目标区间（超出只 WARN），`max_sentences` 是句数上限 |

### `blacklist`（逐项写清，护栏会逐条检查）

两层：条目级（`projects[].blacklist` / `experience[].blacklist`）+ 全局（`global_blacklist`）。

护栏抽「被禁止的字面项」的规则：**引号前面不远处（10 字内）出现否定词**（不得 / 不要 / 不写 / 禁止 / 严禁 / 勿写 / 别写）
才判为禁止。所以：

- ✅ `写「从零实现」，不写「自研引擎」` —— 后面的「自研引擎」被禁，前面的「从零实现」是允许项，**不会误杀**。
- ✅ `**不得写「完全独立完成」「独立开发」**` —— 连续引号共享同一个否定前缀，两个都被禁。

**写黑名单时的正确姿势**：把「允许怎么写」和「禁止怎么写」成对写在一句里，用引号标出被禁的字面词。

## 二、初始化引导（面向新用户的一次性流程）

> 这段是**给 Agent 执行的动作清单**：新用户说「帮我投岗位」时，先做这里，做完再进状态机。

1. **收集来源**：简历（`sources.resume`）、公开仓库（`sources.links`）、用户自述。
   PDF 简历可用 `scripts/pdftext.py` 提文本。
2. **抽取五部分**：身份 / 教育 / 荣誉 / 实习经历 / 项目。
3. **逐条打 `jd_hits`** —— 这条事实能回应哪些 JD 词（技术栈、场景、岗位方向）。**宁多勿缺**。
4. **给项目分档**：哪个主投、哪个第二、哪个第三（写进 `tier` 或 `label_allowed`）。
   分档决定「主攻事实」怎么选。
5. **标 `on_resume` 与 `visibility`**：
   - 不在简历上但公开 ⇒ `on_resume: false`（用时要带链接 + 一句介绍）
   - 私有仓库 ⇒ `visibility: "private"`（**不可用**）
6. **写黑名单**（最容易漏、也最影响可信度）：
   - 这个人**不能被怎么写**（例：不许写"完全独立完成"、不许写"自研引擎"、不许写"上线产品"）
   - 哪些数字**不许出现**（业绩数字）
7. **填 `writing_rules`**：`number_policy`、`number_whitelist`（本人的技术栈）、`must_include`、
   `structure`、`budget`、`focus_aliases`。
   - `focus_aliases` 让护栏能认出主攻事实的**简称**（例：`某项目 id` ← `["项目简称","缩写"]`）。
8. **让用户逐项确认** —— 图谱里的每条事实都会变成自我介绍里的一句话，不能有错。

**投递配置另存 `profile.md`**（同一个数据目录）：简历路径、目标城市、意向标签、薪资判据、循环次数 N。

## 三、建完怎么自检

1. `node scripts/flow.mjs where` —— 确认读的是**用户数据目录**里的图谱（不是旧位置），且 `identity.name` 已填。
2. `node scripts/selftest.mjs` —— 引擎 + 图谱结构一起过（图谱结构断言只在图谱存在时跑）。
3. 随手编一条文案过护栏，确认**本人的技术栈能被正确放行、业绩数字被拦下**：

   ```bash
   python scripts/guard.py --text "<拿一条真文案>" --require "<JD 头号要求原词>" --focus <主攻事实 id>
   ```
4. 把「本图谱的实体清单 / 三项目分工 / 数字纪律」这类**只属于这个人**的笔记写在数据目录里
   （例：`<数据目录>/graph-notes.md`）—— **不要写回 skill 文档**，skill 是要给别人用的。

> 图谱里的实体集合、分档、黑名单都是**因人而异**的：文档只讲判据，具体内容留在数据目录。
